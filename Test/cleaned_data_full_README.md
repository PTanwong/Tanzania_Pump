# cleaned_data_full.csv — คู่มือใช้งาน

ข้อมูล **clean แบบทั่วไป** สำหรับทีมที่ต้องการเอาไปใช้งานเอง (ไม่ใช่ feature
matrix เฉพาะสำหรับเข้าโมเดล) — 59,400 แถว, 42 คอลัมน์

## ต่างจาก `train_values.csv` ต้นฉบับตรงไหน

เก็บ**ทุกคอลัมน์เดิมไว้ครบ** (40 คอลัมน์ + `status_group` จาก `train_labels.csv`)
อ่านง่าย ไม่เข้ารหัสเป็นตัวเลข ไม่ตัดคอลัมน์ทิ้ง แก้เฉพาะปัญหาคุณภาพข้อมูล
3 จุดที่พบตอนทำ EDA:

| คอลัมน์ | ปัญหาที่แก้ | รายละเอียด |
|---|---|---|
| `gps_height` | 0 → `NaN` | 20,438 แถว (34.4%) ที่เป็น 0 ไม่ใช่ความสูงจริงที่ระดับน้ำทะเล แต่เป็นค่า missing ที่เข้ารหัสผิด |
| `population` | 0 → `NaN` | 21,381 แถว (36.0%) เช่นเดียวกัน |
| `construction_year` | 0 → `NaN` | 20,709 แถว (34.9%) เช่นเดียวกัน |
| `longitude`, `latitude` | ค่าที่ผิดปกติ → `NaN` | 1,812 แถว (3.1%) ที่มี `longitude=0, latitude≈0` (จุดกลางอ่าวกินี ไม่ใช่แทนซาเนีย) ถูกตั้งเป็น `NaN` |
| `date_recorded` | แปลงเป็น date type จริง | เดิมเป็น string |
| คอลัมน์ข้อความ (`funder`, `installer`, `subvillage`, `ward`, `lga`, ฯลฯ) | ตัดช่องว่างหัวท้าย | ค่ายังเป็นตัวหนังสือเดิม ไม่ได้แปลงตัวพิมพ์เล็ก/ใหญ่ |

คอลัมน์ใหม่ที่เพิ่มมา **1 คอลัมน์เดียว**: `invalid_coordinates` (True/False) — บอกว่า
แถวนั้นเคยมีพิกัดผิดปกติมาก่อนถูกแก้เป็น `NaN` หรือเปล่า เผื่อทีมอยากกรองแถว
เหล่านี้ออกเองในภายหลัง

## สิ่งที่**ไม่ได้ทำ** ในไฟล์นี้ (ตั้งใจ)
- **ไม่ impute ค่า missing** ที่แปลงเป็น NaN แล้ว (ทั้ง gps_height/population/
  construction_year/lat-lon) — ปล่อยเป็น NaN ตรง ๆ เพราะการ impute เป็นทาง
  เลือกเชิงโมเดล ไม่ใช่ข้อเท็จจริงของข้อมูล ทีมควรเลือกวิธี impute เองตาม
  วัตถุประสงค์การใช้งาน
- **ไม่ตัดคอลัมน์ที่ "ซ้ำซ้อน"** (เช่น `extraction_type` vs
  `extraction_type_group` vs `extraction_type_class`) — เก็บไว้ให้ครบ ให้ทีม
  ตัดสินใจเองว่าจะใช้ระดับไหน
- **ไม่ใส่ feature ที่สร้างขึ้นใหม่** (spatial_cluster, ระยะทางถึงเมือง ฯลฯ)
  — feature พวกนี้อยู่ในไฟล์ `cleaned_train_data_gis.csv` แยกต่างหาก (ดูด้านล่าง)

## ถ้าต้องการไฟล์อื่นแทน
